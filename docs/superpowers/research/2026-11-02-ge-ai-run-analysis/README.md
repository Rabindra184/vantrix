# Gatling Enterprise's AI run analysis, measured

Measured on 2026-11-02 in the `demo-perf` trial org on cloud.gatling.io, on
**Run 2** of test `perfportal-parity-basic` (`example.BasicSimulation`, run
`run_g4gd61dx7fbgmf418wr4rcic9h`, 28 Oct 2026, 1m 31s, 1,724 requests). This is
backlog item #11's first step: until today the card's OUTPUT had never been
seen, because clicking it starts a generation.

## What it is

- **Where:** a card on the run's **Summary**, between the run metadata and the
  lifecycle strip. Before generation it reads "AI run analysis — NEW IN
  GATLING · Let the magic happen and get a full report analysis on your run in
  minutes", with one button, **Analyze with AI**.
- **Cost:** none visible. The org had **0 credits** ("You have no credits
  left") and generation still ran. No confirmation, no consent dialog, no
  tooltip.
- **Time:** about 20 seconds, behind "AI run summary is loading…".
- **Stored per run:** after a reload the analysis is served immediately by
  `GET /api/private/runs/{runId}/ai-report`, fetched beside
  `GET /api/private/runs/{runId}`. The card header then says
  "Generated on 02/11/2026".
- **Controls:** three **Collapse** buttons, one per section, and nothing else.
  No regenerate, edit, copy, feedback or "generated by AI" disclaimer beyond
  the card's title.
- **Org switch:** Organization → Settings → Features management →
  **AI features** ("Allows users to generate and view AI-powered reports"),
  enabled on this trial org. `org-ai-setting.jpg`.

## Its shape

Three sections. Each has an icon, a CAPS label, ONE bold headline sentence,
and bullets under it (`card-top.jpg`, `card-bottom.jpg`):

```
HEALTH            headline + 4 bullets
INSIGHTS          headline, then a two-column grid of four sub-sections:
                    ERRORS (3)        ASSERTIONS (3, one per assertion)
                    INJECTION PROFILE (2)  RESPONSE TIMES (3)
RECOMMENDATIONS   headline + 5 bullets
```

## Checked against the run's own Report

Every figure was compared with the same run's Requests table and Errors table.

**Copied correctly:** total 1,724, KO 289 = 16.76%, throughput 18.95/s, global
P95 321 / P99 2383 / max 4159 / mean 150 / SD 387 ms, max VUs 15, every error
count and share (170 / 60 / 31 + 28 / 16), Place Order 172 total, 0 OK, 172
KO, P95 195 / P99 2143 / max 2191, and the three assertions with their actuals.

**Wrong or misleading:**

1. **Double counting.** "172 Place Order failures plus 170 401s/other auth
   errors cause a 16.76% KO rate" adds to 342. The run had **289** KO in total:
   Place Order's failures ARE among those 401/403/404 responses.
2. **The tail was attributed to nothing, and its real source was missed.**
   The global max (4159 ms) and P99 come from **Add To Cart** (P95 555, P99
   4095, max 4159 ms; 0 KO), which the analysis never mentions. It names
   Place Order, which "is not the primary latency issue", and stops there.
3. **The end of the run read as a failure.** "At timestamps 88–90 …
   successful responses drop to zero … a systemic functional failure point":
   the chart does show OK reaching zero in the last 2–3 seconds, but that is
   the run's tail, when the only requests left are each user's last step,
   Place Order (100% KO). And "timestamps 88–90" carries no unit.
4. **Inconsistent within itself.** "~59 occurrences of 403 variants" in
   Errors, "28+403s" in Recommendations.
5. **Raw machine values.** "actual = 83.23665893271462%", "172.0 failures",
   "4159.0 ms": numbers passed through without formatting.

So the numbers it COPIES are right, and the claims it DERIVES (sums,
attributions, readings of a chart) are where it goes wrong. That is the
distinction a PerfPortal version has to design around.
