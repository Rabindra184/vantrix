# Trends (Phase 1a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A run in the context of its history — one new endpoint returning the run's cohort, and a fourth run tab drawing status, percentiles and throughput across runs.

**Architecture:** One new read-only endpoint, `GET /v1/runs/:id/trends`, in the existing `/v1/runs/:id/*` family so it inherits that family's tenant scoping verbatim. It joins `run` to the run-scope `run_stat` row already stored — no new aggregation, no migration, no ingest change. The web side is a transform plus three charts on a new route, reusing `Chart` and its `DataTable`.

**Tech Stack:** NestJS, Prisma + raw SQL (`pg`), PostgreSQL, Zod contracts, React 18.3.1, TypeScript, ECharts, TanStack Query, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-15-cross-run-analysis-and-report-completeness-design.md` (§1.1, §1.2, §1.4, §1.5 — Trends only; §1.3 Compare is a separate plan)

## Global Constraints

- **Node ≥22.** On v20 jsdom cannot load and `pnpm test:unit` prints a green-looking count beside 20 unhandled errors and exit 1, silently skipping every jsdom suite. Check `node -v` before trusting a pass.
- **`?name=X` without `scope` is silently ignored.** The metrics endpoints force `name` to `''` when `scope` is absent. Both parameters, always — and test the omission, not just the correct call.
- **Every new e2e `getByRole(role, { name })` passes `exact: true`.** `ProjectRail` renders `All runs` plus one link per project in every authenticated document, and Playwright's default name match is a case-insensitive substring.
- **No `uppercase` on anything queried by accessible name.** Playwright applies `text-transform` when computing accessible names; jsdom does not.
- **No decorative `<svg>` inside a chart `<figure>`.** `run-charts.spec.ts` proves a chart drew by counting SVG elements within the figure.
- **Expectations are computed from the payload, never written down.**
- **Null is not zero.** A gap is `null` and draws as a gap; a missing cell is `—`.
- **Verification gate** before any task is done: `pnpm typecheck && pnpm lint && pnpm test:unit`; before the plan is done, additionally `pnpm test:integration && pnpm test:e2e` with the local stack up.

- [ ] **Step 1: Write the schema**

```ts
/**
 * One run in a cohort, as the trends endpoint reports it: run identity plus
 * the run-scope `StatRow` already stored for it.
 *
 * NOT a `StatRow` with extra fields. `StatRow` carries `scope`, `name`,
 * `family` and `indicators`, and every one of those is either constant across
 * this response (`scope: 'run'`, `name: ''`, `family: 'response_time'`) or a
 * fold at project settings this endpoint does not read. Reusing it would ship
 * four fields per run that mean nothing here.
 */
export const TrendRunSchema = z.object({
  id: z.string().uuid(),
  startedAt: z.string().datetime(),
  /** The tool's own start. Null until the worker parses the run header. */
  toolStartedAt: z.string().datetime().nullable(),
  durationMs: z.number().int().nullable(),
  verdict: z.enum(['passed', 'failed', 'not_evaluated']).nullable(),
  count: z.number().int(),
  okCount: z.number().int(),
  koCount: z.number().int(),
  errorRate: z.number(),
  minMs: z.number(),
  maxMs: z.number(),
  meanMs: z.number(),
  throughputRps: z.number(),
  /** Keys are p<number>, exactly as StatRow's are. */
  percentiles: z.record(z.number()),
});
export type TrendRun = z.infer<typeof TrendRunSchema>;

/**
 * `GET /v1/runs/:id/trends` — the asked-about run in the context of its
 * cohort.
 *
 * THE COHORT IS (project, simulation), with NULL as its own equivalence class
 * rather than a wildcard. Two runs that both lack a simulation name are
 * grouped because they match by the same rule, and the UI says the grouping is
 * by absence rather than claiming they are the same test.
 *
 * `runs` IS NEWEST FIRST, matching `/v1/runs`. A trend reads left-to-right in
 * time, so the chart transform reverses it — stated here so the two cannot
 * drift into reversing it twice or not at all.
 *
 * `cohortSize` IS NOT `runs.length`. A reader looking at twenty of sixty runs
 * has to be told, rather than shown a truncated history that looks complete.
 */
export const TrendsResponseSchema = z.object({
  runId: z.string().uuid(),
  /** The cohort key. Null is a real cohort, not "unknown". */
  simulation: z.string().nullable(),
  /** Total runs matching the cohort, which may exceed `runs.length`. */
  cohortSize: z.number().int(),
  runs: z.array(TrendRunSchema),
});
export type TrendsResponse = z.infer<typeof TrendsResponseSchema>;
```

- [ ] **Step 1: Write the SQL module**

Create `packages/persistence/src/metrics/trends.ts`:

```ts
/**
 * The cohort query behind `GET /v1/runs/:id/trends`.
 *
 * ═══ WHY EVERY PART OF THE JOIN PREDICATE IS THERE ═══
 *
 * `run_stat` has a UNIQUE index on (run_id, scope, name, family). Filtering
 * ALL FOUR is what makes this join return exactly one row per run. Joining on
 * `scope = 'run'` alone would fan out the moment a run carries a run-scope row
 * for a second family — and the failure is silent and ugly: the same run
 * appears twice in the trend, at the same timestamp, with different numbers.
 *
 * `name = ''` is the run-scope row's own name, not a placeholder. `family =
 * 'response_time'` is the family the statistics table already treats as the
 * run's totals.
 *
 * ═══ IS NOT DISTINCT FROM ═══
 *
 * `simulation = $3` is wrong for the NULL cohort: in SQL, NULL = NULL is NULL,
 * so a run with no simulation name would match nothing, including itself. `IS
 * NOT DISTINCT FROM` is the operator that treats two NULLs as equal, and it is
 * exactly the equivalence class the spec asks for.
 *
 * ═══ ONLY TERMINAL RUNS ═══
 *
 * A `pending` or `parsing` run has no `run_stat` row at all, so the inner join
 * already excludes it. `status = 'complete'` is stated anyway: it makes the
 * intent readable, and it excludes a `failed` run, which CAN have partial
 * stats and would put a spurious dip in a trend.
 *
 * ═══ ORDERING ═══
 *
 * `COALESCE(tool_started_at, started_at) DESC` — the same effective ordering
 * key `RunRepository.list` uses, so the trend and the run list agree about
 * what "most recent" means. Newest first; the chart transform reverses.
 *
 * No index covers (project_id, simulation, COALESCE(...)). Neither does
 * `RunRepository.list`'s ordering, and for a cohort of a few hundred runs the
 * sort is cheap. If a project ever holds enough runs for this to matter, the
 * fix is an index, not a different query — recorded here so the next reader
 * does not rediscover it.
 */
export const TRENDS_SQL = `
  SELECT r.id, r.started_at, r.tool_started_at, r.duration_ms, r.verdict,
         s.count, s.ok_count, s.ko_count, s.error_rate,
         s.min_ms, s.max_ms, s.mean_ms, s.throughput_rps, s.percentiles
    FROM run r
    JOIN run_stat s
      ON s.run_id = r.id
     AND s.org_id = r.org_id
     AND s.project_id = r.project_id
     AND s.scope = 'run'
     AND s.name = ''
     AND s.family = 'response_time'
   WHERE r.org_id = $1 AND r.project_id = $2
     AND r.simulation IS NOT DISTINCT FROM $3
     AND r.status = 'complete'
   ORDER BY COALESCE(r.tool_started_at, r.started_at) DESC, r.id DESC
   LIMIT $4`;

/** The same predicate, counted. Separate rather than a window function so the
 *  LIMIT above cannot silently cap the total it is meant to be compared with. */
export const COHORT_SIZE_SQL = `
  SELECT COUNT(*)::int AS size
    FROM run r
    JOIN run_stat s
      ON s.run_id = r.id
     AND s.org_id = r.org_id
     AND s.project_id = r.project_id
     AND s.scope = 'run'
     AND s.name = ''
     AND s.family = 'response_time'
   WHERE r.org_id = $1 AND r.project_id = $2
     AND r.simulation IS NOT DISTINCT FROM $3
     AND r.status = 'complete'`;

export interface StoredTrendRun {
  readonly id: string;
  readonly startedAt: Date;
  readonly toolStartedAt: Date | null;
  readonly durationMs: number | null;
  readonly verdict: string | null;
  readonly count: number;
  readonly okCount: number;
  readonly koCount: number;
  readonly errorRate: number;
  readonly minMs: number;
  readonly maxMs: number;
  readonly meanMs: number;
  readonly throughputRps: number;
  readonly percentiles: Record<string, number>;
}
```

- [ ] **Step 2: Add the reader method**

In `packages/persistence/src/metrics/read.ts`, import from `./trends` and add to `MetricReader`:

```ts
  /**
   * Two queries, not one. A window-function count alongside the LIMITed rows
   * would be one round trip, but the count is the thing that tells a reader
   * their twenty rows are twenty of sixty — computing it inside the same
   * limited query is exactly how it comes back as twenty.
   */
  async trends(
    scope: ProjectScope,
    cohort: { simulation: string | null },
    limit: number,
  ): Promise<{ runs: StoredTrendRun[]; cohortSize: number }> {
    const params = [scope.orgId, scope.projectId, cohort.simulation];

    const [rows, size] = await Promise.all([
      this.pool.query(TRENDS_SQL, [...params, limit]),
      this.pool.query(COHORT_SIZE_SQL, params),
    ]);

    return {
      runs: rows.rows.map((r) => ({
        id: r.id,
        startedAt: r.started_at,
        toolStartedAt: r.tool_started_at,
        durationMs: r.duration_ms,
        verdict: r.verdict,
        count: r.count,
        okCount: r.ok_count,
        koCount: r.ko_count,
        errorRate: r.error_rate,
        minMs: r.min_ms,
        maxMs: r.max_ms,
        meanMs: r.mean_ms,
        throughputRps: r.throughput_rps,
        percentiles: r.percentiles as Record<string, number>,
      })),
      cohortSize: size.rows[0]?.size ?? 0,
    };
  }
```

```ts
  /**
   * A run in the context of its cohort — every run of the same simulation in
   * the same project.
   *
   * RUN-SCOPED RATHER THAN PROJECT-SCOPED (`/v1/projects/:slug/trends`)
   * because it needs no slug resolution and no new authorization reasoning:
   * `#run` already resolves and tenant-checks exactly as its siblings do. It
   * also matches how a reader arrives — from a run, wanting that run in
   * context.
   */
  @Get('trends')
  @Scopes('read')
  async trends(
    @Param('id', uuidParam('id')) id: string,
    @Req() req: Request,
    @Query('limit') limit = '20',
  ): Promise<TrendsResponse> {
    const run = await this.#run(req, id);

    const { runs, cohortSize } = await this.reader.trends(
      { orgId: run.orgId, projectId: run.projectId },
      { simulation: run.simulation ?? null },
      parseLimit(limit),
    );

    return {
      runId: run.id,
      simulation: run.simulation ?? null,
      cohortSize,
      runs: runs.map((r) => ({
        id: r.id,
        startedAt: r.startedAt.toISOString(),
        toolStartedAt: r.toolStartedAt?.toISOString() ?? null,
        durationMs: r.durationMs,
        verdict: (r.verdict ?? null) as TrendsResponse['runs'][number]['verdict'],
        count: r.count,
        okCount: r.okCount,
        koCount: r.koCount,
        errorRate: r.errorRate,
        minMs: r.minMs,
        maxMs: r.maxMs,
        meanMs: r.meanMs,
        throughputRps: r.throughputRps,
        percentiles: r.percentiles,
      })),
    };
  }
```

```ts
import type { TrendsResponse } from '@perfportal/contracts';
import type { ChartData, ChartSeries, ChartTableRow } from '../types';

/**
 * `TrendsResponse` → the three trend figures.
 *
 * THE X AXIS IS CATEGORICAL, ONE SLOT PER RUN, and that is a decision rather
 * than a convenience. Runs are not evenly spaced in time — three in an hour
 * during a debugging session, then nothing for a week — and a time axis would
 * draw that gap as a long flat stretch, inviting the reader to see a rate of
 * change between runs that nothing measured. The question this chart answers
 * is "run over run", so the axis is runs.
 *
 * THE RESPONSE IS NEWEST FIRST and every transform here reverses it, because a
 * trend reads left-to-right in time. Done once, in `ordered`, so three charts
 * cannot disagree about direction.
 */

/** Oldest first — see the file docstring. */
function ordered(t: TrendsResponse): TrendsResponse['runs'] {
  return [...t.runs].reverse();
}

/**
 * A short, sortable label per run. The full timestamp and the run id go in the
 * table, which is where a reader goes to identify a specific point.
 */
function label(run: TrendsResponse['runs'][number]): string {
  const at = new Date(run.toolStartedAt ?? run.startedAt);
  return at.toISOString().slice(5, 16).replace('T', ' ');
}

/**
 * Set when the cohort is longer than the window. A reader shown twenty of
 * sixty runs, with nothing saying so, reads a complete history.
 */
function truncation(t: TrendsResponse): string | undefined {
  if (t.cohortSize <= t.runs.length) return undefined;
  return `Showing the most recent ${t.runs.length} of ${t.cohortSize} runs in this cohort.`;
}
```

Then each transform. Status is percentages (`count === 0` → `null` for both, never `0/0` — a run that recorded nothing is not a run that succeeded nothing); percentiles are one series per key present, sorted numerically off the payload's own keys, with an absent key a `null`; throughput splits `throughputRps` by `errorRate`. Every one returns the `empty` reason for a zero-length cohort and carries `truncation(t)` as `limitation`.

```ts
export const trendsQueryKey = (id: string, limit: number) =>
  ['run', id, 'trends', limit] as const;

/**
 * `staleTime: Infinity` is WRONG here and is deliberately absent.
 *
 * Every other factory in this file has it because a completed run's own
 * metrics are fixed the moment it is ingested. A COHORT is not: ingesting a
 * new run of the same simulation changes this answer without changing any run
 * in it. So this query is allowed to go stale and refetch on mount, which is
 * exactly the behaviour the rest of the file suppresses.
 */
export const trendsQuery = (id: string, limit = 20) => ({
  queryKey: trendsQueryKey(id, limit),
  queryFn: () =>
    apiFetch(TrendsResponseSchema, `${runPath(id)}/trends?limit=${limit}`),
});
```
