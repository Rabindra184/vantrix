# Request detail page (§13.3, RQ-01…RQ-11) — design

Piece 3 of the parity family. Builds the page behind
`/runs/:runId/requests/:name`, which piece 2 links to and
`DetailPlaceholder` currently answers with an honest "not built yet".

It opens by resolving **D-10**, the request-identity deviation recorded in the
parity-tables spec §6a and deferred to this piece. That is task 1, not a
closing tidy-up, for the reason in §2.

---

## 1. Scope

The eight containers §13.3 specifies, confirmed present in the reference
report:

```
RangesContainerId · responseTimeDistributionContainerId
responseTimeOverTimeContainerId · requestsContainerId · responsesContainerId
responseTimeScatterContainerId · container_errors
```

Note the request page titles its charts differently from the global page —
`Number of requests`, not `Requests per second`. Same data, different heading;
the parity assertions must read the request page's own titles.

**RQ-04, RQ-06 and RQ-10 do not exist.** A case-insensitive search of the
generated report returns zero occurrences of "latency": Gatling 3.15.1.2
reports response time only (§A.9 F-2). The latency elements stay gated behind
the `latency` plugin capability and are not rendered here. This is settled, not
re-opened.

In scope: RQ-01, RQ-02, RQ-03, RQ-05, RQ-07, RQ-08, RQ-09, RQ-11.

## 2. Task 1: D-10 — request identity becomes the group path

`packages/statistics/src/engine.ts:133` rolls a group up under
`e.groups.join('/')`. Thirty-eight lines later, `:171` rolls a request up under
the bare `e.name`, and the group stack it arrived with is discarded.

Requests become `[...e.groups, e.name].join('/')`, matching what `:133`
already does for groups.

### 2a. Why this is first, and why the usual argument for it is the weak one

The parity-tables spec deferred D-10 on the grounds that piece 3 owns request
identity because it builds `/runs/:id/requests/:name` for real. That is true
and it is the weaker argument: `detailPathFor` carries `row.path` whatever
`row.path` happens to contain, and the placeholder it points at is a dead end
with no compatibility surface.

The load-bearing argument is that **piece 2 already shipped a tree that cannot
nest requests, and it is visible in the product today.**

`apps/web/src/tables/buildTree.ts:164` parents a row purely by `/`-prefix
against the indexed groups. A request carrying the bare name `List Products`
has no `/`, so `parentPathOf` returns `null`, and it falls to the root through
the orphan rule at `:174`. Groups nest correctly; every request sits flat
beside them regardless of the group it actually ran in.

Against the reference run that is 5 of 7 requests in the wrong place —
`Related Items` belongs under `Catalog/Recommendations`; `List Products` and
`Product Detail` under `Catalog`; `Add To Cart` and `View Cart` under `Cart`;
only `Search` and `Place Order` genuinely sit at root.

So D-10 is not preparation for this piece. It is the missing half of the
previous one, and the statistics table is wrong on screen until it lands.
That is a materially easier call than "a design decision deferred a third
time", and it is why this is task 1.

**Nothing upstream needs to change.** The Gatling plugin already reads the
group stack and carries it on every request event
(`packages/plugin-gatling/src/records.ts:34`, into `RequestEvent.groups` at
`packages/core/src/events.ts:17`). This is a pure engine-side join: no plugin
change, no re-parse, no new capability flag.

**Nothing downstream needs to change either.** `buildTree` splits *any* row's
name on `/`, so the day the engine emits the joined name, requests nest with
no rendering change — and `apps/web/test/buildTree.test.ts` already proves it
with a test driven by a renamed request.

### 2b. The blast radius is six sites, not three

The parity-tables spec measured three — series, stats, errors. There are four
`e.name` sites in the request branch of the engine, plus two artefacts that are
not engine code and are the easiest of the six to miss: a captured fixture, and
an e2e spec whose assertions encode the flat behaviour on purpose.

| # | Site | What it is | Consequence of missing it |
|---|------|-----------|---------------------------|
| 1 | `engine.ts:164` | `seriesFor('request', e.name, …)` | charts key on a different name than stats |
| 2 | `engine.ts:171` | `rollupFor('request', e.name, 'response_time')` | the statistics row |
| 3 | `engine.ts:178` | `errorsFor('request', e.name)` | RQ-11 finds nothing |
| 4 | `engine.ts:147` | `endpoints.add(e.name)` | **see §2c — this one changes behaviour** |
| 5 | `apps/web/test/fixtures/reference-run.json` | captured payload, regenerated by `scripts/capture-chart-fixture.mjs` | every web test asserting a bare request name fails against a stale capture |
| 6 | `apps/web/e2e/run-tables.spec.ts:103`, `:182` | `openingPaths` counts all 7 requests at root, and asserts every rendered row has `data-depth="0"` | the e2e suite fails **because the fix worked** |

Site 6 is worth its own line because it does not read as a consequence of
D-10 — it reads as a regression. The spec's own header comment (`:27`) states
that the flat rows are D-10 and not a bug there; when D-10 lands, the reference
run's opening rows become 2 root groups plus the 2 genuinely-rootless requests,
depths are no longer uniformly `'0'`, and the `.toBe(9)` count is wrong. Change
that file **in the same commit** as the engine, or the next reader bisects a
green-to-red transition into the one commit that fixed the thing.

Site 5 sequences the work: recapture the fixture immediately after the engine
change and before touching the web tests, or the web suite fails for two
unrelated reasons at once and each one hides the other.

Tests pinning bare names, to be updated with the change rather than after it:

- `packages/statistics/test/scopes.test.ts:24` — `['A','B','C']` becomes
  `['C','G1/A','G1/B']` once sorted. `C` has `groups: []` and correctly stays
  bare, which is the root case still behaving.
- `packages/statistics/test/engine.test.ts:35` — the `'buy'` error rollup. This
  one passes **untouched**, because both its request events carry `groups: []`
  — which is exactly why it should gain a group and assert `Checkout/buy`.
  Site 3 (`errorsFor`) has no other direct guard, and a test that would not
  have caught the regression is not covering the line it appears to cover.
- `apps/web/test/buildTree.test.ts` — the assertions naming `'Related Items'`
  (`:231`) and `'Search'` (`:354`, `:368`).

`buildTree.test.ts:157` derives its expectation from the payload rather than
hard-coding names, so it survives untouched. That is the pattern the others
should be moved to where it costs nothing.

### 2c. Deviation D-12: the cardinality cap now counts paths

`engine.ts:147` is the site with a behavioural consequence, and it is why this
is a design decision rather than an implementation detail.

`endpoints` is a `Set` feeding two things: the `ENDPOINT_CARDINALITY_EXCEEDED`
guard at `:148` and `endpointCount` on the result. Key the rollups on the
joined path while the cap keeps counting bare names, and the cap stops
bounding the thing it exists to bound — 500 distinct names appearing under
four groups each counts as 500 and stores 2000 rollups. The cap's entire job
is bounding rollup cardinality, so it must count what is actually stored.

**Decision: `endpoints.add(name)` takes the joined path too.**

The consequence is stated rather than discovered: for a grouped run, the same
simulation now counts nearer its true rollup count, so a run close to the
2000 ceiling can begin failing ingest where it previously passed. That is the
cap doing its job correctly for the first time, but it is a threshold change
and it belongs in the ledger as **D-12**.

`scopes.test.ts:27`'s cap test uses `groups: []` throughout and so is
unaffected — which makes it a poor guard for this. Add a grouped case.

### 2d. No backfill — and the `started_ok_count` precedent does not transfer

Runs ingested before this change keep their bare names and render flat, as
they do today. No migration, no re-aggregation.

The argument for that should **not** be "consistent with the
`started_ok_count` precedent", because the defining feature of that precedent
is the opposite. Those columns are nullable *and* flagged, and the UI says so
in words: `startedSplitAvailable` reaches the chart, and
`apps/web/src/charts/transforms/rates.ts:127` renders `SPLIT_UNAVAILABLE`
precisely so a reader cannot mistake "not recorded" for "nothing failed".

D-10 has no such flag. A pre-change run renders its requests at the root,
indistinguishable from a run whose requests genuinely had no groups.

Skipping the backfill is still right, but the honest justification is the
orphan rule, not that precedent: both runs render correctly and truthfully,
the old one just renders flatter. Nothing is claimed about an old run that is
false — which is the actual bar `SPLIT_UNAVAILABLE` was written to meet.

### 2e. Deviation D-13: SLA rules match a bare target leniently

Found reviewing Tasks 1–2, and not anticipated by §2b's blast radius — which
measured the engine, its tests and the web artefacts, and missed a consumer one
package away.

`packages/sla/src/evaluate.ts:44` finds a rule's stat by exact name. After D-10
a request-scoped rule whose `targetName` is `List Products` matches nothing,
takes the `!stat` branch, and reports `outcome: 'not_applicable'` — "so the
rule was not checked."

**An SLA gate that stops enforcing while looking healthy is the worst failure
mode in this change.** §2d's no-backfill decision sharpens it: pre-D-10 runs
keep bare names, so such a rule keeps passing on old runs and silently stops on
new ones, with nothing in the product looking wrong.

**Decision: lenient matching, not a migration.** Exact match first, then the
leaf segment. A migration rewriting stored targets to joined paths would fix
new runs and break the same rules against the old ones that keep bare names by
design — wrong on one side of the boundary either way.

Applied at every non-run scope, including groups, whose names have always been
paths and where a bare target has therefore never matched. One matching
behaviour: a reader debugging a rule should not have to know which scope
changed identity when.

**Ambiguity is not resolved by picking.** `Cart/View` and `Catalog/View` both
end in `View`; choosing one silently would be a worse bug than the one being
fixed. The outcome vocabulary is fixed in the contract
(`packages/contracts/src/run.ts:9`), so an ambiguous target stays
`not_applicable` — with a message naming the candidates, which is a different
sentence from "there were no statistics".

Deferred, deliberately: whether rule authoring should offer the joined path.
That is a question about the rule-editing surface, not about this change.

## 3. Route identity was decided in piece 2, and stays decided

The route carries the full path encoded as **one segment**. This is not an
open choice in this piece; it shipped with the statistics table:

- `apps/web/src/App.tsx:42` — `/runs/:runId/requests/:name`, a single dynamic
  segment, with the comment rejecting the splat spelling: it would match the
  same URLs and hand piece 4 a splat to reassemble, "one more place for the
  separator rule to be got wrong".
- `apps/web/src/tables/StatisticsTable.tsx:822` — `detailPathFor` encodes
  `row.path` with `encodeURIComponent`, so `Catalog/Recommendations` leaves as
  `Catalog%2FRecommendations`.
- `apps/web/src/routes/DetailPlaceholder.tsx:29` — `useParams` decodes it
  back, one param carrying a full path.

This piece inherits it and piece 4 inherits it for free. The design records it
so it is found rather than re-argued.

### 3a. The one thing the existing comments do not cover

`%2F` survives client-side navigation because `pushState` never touches it.
A **hard load** of an encoded URL — a paste, a reload, a bookmark, a
`?next=` round-trip through the login page — goes through the server first,
and if anything in that path normalises `%2F` to `/` before the SPA fallback,
the URL arrives as extra segments, matches no route, and `App.tsx:53`'s
catch-all redirects to `/runs`. The reader loses their run silently, which is
the exact failure `DetailPlaceholder` exists to prevent.

Traced against our own server, this works: `mountSpa`
(`apps/api/src/spa.ts:42`) reads `req.path`, which Express does not
percent-decode, so `isApiPath` sees the encoded form; `express.static` misses
and falls through to `res.sendFile(index.html)`; React Router then matches
against `window.location.pathname`, which still holds `%2F`.

But that is the behaviour of two dependencies rather than of our code, and a
proxy or CDN in front of it can undo it. **Requirement: an e2e that hard-loads
an encoded request URL with `page.goto()` rather than clicking through to
it.** Clicking through only ever exercises `pushState` and will pass whatever
the server does.

## 4. What is reuse and what is new

Six of the eight elements are charts piece 1 already built, and their
transforms take a payload rather than a scope — `toDistribution`,
`toPercentiles`, `toRequestRate` and `toResponseRate` work unchanged at
request scope. The endpoints already accept `?scope=request&name=`, and
`seriesQuery`/`distributionQuery`/`errorsQuery` already take `scope` and
`name` arguments defaulting to the run (`apps/web/src/api/metrics.ts:75`,
`:116`, `:175`) — written that way in piece 1 for exactly this page, so no
second fetcher is needed.

**One exception to "unchanged", found against the reference report:** the two
rate charts are titled differently on a request page —
`fixtures/gatling-3.15.1.2/reference-report/req_search--1822469688.html` heads
them **`Number of requests`** and **`Number of responses`** where the global
page says "Requests per second over time" and "Responses per second over time".
Same payload, same transform, same axis; only the heading differs, so
`RequestRateChart`/`ResponseRateChart` take an optional `title` rather than
being forked.

So most of this piece is routing and fetching at a different scope. What is
genuinely new:

- **RQ-09**, the saturation scatter — §5.
- **RQ-01/RQ-02**, the statistics row and indicator bands for one request,
  reusing piece 2's row rendering and piece 1's `IndicatorsChart`.
- **RQ-11**, errors for this request, reusing piece 2's `ErrorsTable` at
  request scope — §6.

## 5. RQ-09: the saturation scatter

`ScatterResponse` exists and is parity-tested. The shape is the part most
easily got wrong, and §A.9 F-7 records that it was got wrong once already:

**It is not a per-request scatter. It is one point per second.** x = global
requests/s across the whole run, both statuses combined; y =
`digest.quantile(0.95).toInt` — **truncated, not rounded**. The two series are
independent status filters, not a split of one.

The fixture alone cannot falsify this: p75 through max coincide on all seven
request pages at ~3 requests/second. Assertions go against ground truth, per
§A.2's tolerance for this row.

**Expect two points to disagree with Gatling, and do not fix them.** Deviation
D-03: our bucketing floors an observation into its bucket where Gatling rounds
to nearest, because floor is scale-consistent and nearest breaks AC-STAT-2's
lossless-coalescing invariant. Measured cost against the fixture: `Add To Cart`
48 points vs Gatling's 47, `Place Order` 53 vs 54. KO counts are exact (15 and
9) on both. A test that "corrects" these is reintroducing a reverted change.

## 6. RQ-11 and the `?name=` trap

Errors at request scope reuse `ErrorsTable` unchanged. The one hazard is
documented at `apps/web/src/api/metrics.ts:149` and is worth restating because
this page is its first real caller:

**`?name=Search` without `scope` is silently ignored.** The reader's ternary
forces `name` to `''` when `scope` is absent, so the request returns
run-scoped errors with a 200 and no indication that the filter was dropped —
the whole run's errors presented as one request's. Both parameters, always.

A test must cover the omission, not just the correct call: assert that request
scope with a name returns fewer errors than the run, so a silently-dropped
filter fails rather than passing with plausible-looking data.

## 7. Architecture

```
apps/web/src/routes/
  RequestDetail.tsx     replaces DetailPlaceholder for the request route
apps/web/src/charts/
  ScatterChart.tsx      new — RQ-09
  transforms/scatter.ts new — pure, ScatterResponse -> ChartData
```

`DetailPlaceholder` stays, still serving `/runs/:runId/groups/:name` until
piece 4 replaces it. Its `kind` prop already carries that split, so the change
here is one route element.

`RequestDetail` composes existing chart components against `useParams().name`
and changes no chart internals. If it needs a chart to behave differently at
request scope, that is a signal the transform boundary is wrong and belongs in
a review, not a prop.

## 8. Testing

The same three layers as pieces 1 and 2: pure unit tests against the
recaptured fixture; the rendered page as its own parity surface; Playwright
for what only exists in a browser.

Two additions specific to this piece:

1. **The hard-load test in §3a** — `page.goto()` on an encoded URL, not a
   click-through.
2. **A grouped cardinality-cap case** (§2c), since the existing cap test uses
   `groups: []` and cannot see the change.

Per piece 2's rule, at least two falsification checkpoints must name a
non-numeric mutation. Checkpoints 4 and 6 below are this piece's.

## 9. Falsification checkpoints

| # | Break this | This must fail |
|---|-----------|----------------|
| 1 | revert `engine.ts:171` to the bare `e.name` | requests nest under their groups in the statistics table |
| 2 | leave `engine.ts:147` counting bare names | the cap counts what is stored, not what is displayed |
| 3 | round RQ-09's p95 instead of truncating | the scatter matches ground truth |
| 4 | drop `scope` from the RQ-11 errors call, keeping `name` | request errors are a strict subset of the run's |
| 5 | render RQ-05 from the combined percentile set instead of the OK set | the percentiles chart excludes KO responses (§A.9 F-11) |
| 6 | serve an encoded request URL through a `%2F`-normalising proxy | a hard-loaded encoded URL reaches the page, not `/runs` |
| 7 | render the latency elements when the capability is absent | no latency chart appears for a Gatling run (§A.9 F-2) |

Checkpoint 6 is the one most likely to be skipped as environmental. It is the
one that loses a reader's run in production.

## 10. Success criteria

A person clicks a request row in a run's statistics table and lands on a page
showing that request's own statistics, indicator bands, response-time
distribution, percentiles over time, request and response rates, the
saturation scatter, and its errors — reachable by pasting the URL as well as
by clicking. Requests nest under their groups in the statistics table of every
newly ingested run. `pnpm typecheck`, `pnpm lint`, the unit, integration and
Playwright suites are green, and every checkpoint in §9 has been run and shown
to fail as named.

D-10 moves from deferred to resolved in the ledger; D-12 is recorded.
